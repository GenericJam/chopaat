# Cell transforms: precomputed JSON extracted from the board GLBs

- Date: 2026-08-30
- Bead: `chopaat-mgw`
- Status: accepted

## Context

Pawn placement needs the world position of every board cell. The board
assets already carry them: each cell exports a named glTF node (an empty
at the cell's top surface, `cell_t{track}_l{lane}_r{row}`, plus
`base_t*_seat_*` and `center_home` — `assets/scripts/README.md`), and the
rules engine's `Chopaat.Board.cell_name/1` speaks the same addressing. So
the placement pipeline is: engine lap position → `Board.cell/3` →
`Board.cell_name/1` → node translation.

## Decision

**Precomputed, committed JSON, regenerated by a mix task.**

- `Chopaat.Glb` reads a `.glb`'s JSON chunk (pure Elixir, `:json`, never
  touches buffer data). The cell nodes are root-level with plain
  `translation` arrays — no hierarchy walk needed (verified for both
  boards).
- `mix chopaat.gen.cells` snapshots both boards' placement nodes into
  `priv/assets/board_cells.json` (117 nodes for 4p, 175 for 6p).
- `Chopaat.Scene.BoardMap` embeds that JSON at compile time
  (`@external_resource`) and serves `position/2`.

Why a committed snapshot instead of parsing the GLB at runtime: app boot
shouldn't parse 1 MB of GLB for ~300 vec3s, the diff makes transform
changes reviewable, and compile-time embedding keeps `Chopaat.Scene` a
pure function with no filesystem dependency at render time.

Staleness is gated, not hoped for: `test/chopaat/board_map_test.exs`
re-derives the table from the GLBs and fails if the snapshot drifts, and
also asserts every position the engine can produce (every lap position ×
player, both player counts, all base seats) resolves to a node present in
the table.

## Consequences

- Any board-asset regeneration must be followed by
  `mix chopaat.gen.cells`; forgetting fails the suite with the command to
  run.
- Rotations are not snapshotted (cells are axis-aligned empties); the
  tipped-pawn pose and shell orientations are composed in `Chopaat.Scene`.
